# eBook Tools Suite — Framework Execution

I’ve applied the framework you established. The result is a **product/technical architecture specification**, not an implementation plan.

The suite is designed as a professional **eBook creation, editing, formatting, publishing, and analysis environment**, with browser-native functionality separated from AI-dependent functionality.

# 1. Reference-Suite Research

The research shows that modern eBook tooling is not merely a word processor. The strongest systems combine several layers:

* manuscript authoring
* structured chapters and sections
* typography and book styling
* front/back matter management
* automatic table of contents
* image/media management
* hyperlinks and navigation
* eBook previewing
* EPUB export
* print/PDF export
* accessibility validation
* publishing preparation
* collaboration/review
* cover creation
* device-specific preview

E.g. Reedsy's Studio combines writing, editing, chapter organization, themes, front matter, collaboration, previewing and EPUB/PDF export. ([Reedsy][1])

[Reedsy Studio](https://reedsy.com/studio/?utm_source=chatgpt.com)

Amazon's Kindle Create similarly separates a book into front matter, body and back matter, supports themes, TOCs, images, hyperlinks and previewing. ([Amazon Kindle Direct Publishing][2])

[Kindle Create documentation](https://kdp.amazon.com/en_US/help/topic/G93BCLJGZFGK39BT?utm_source=chatgpt.com)

The important architectural conclusion is:

> **An eBook suite should be treated as a structured publishing system, not simply a rich-text editor.**

# 4. Layout Engine

The suite should support two fundamentally different publishing modes.

## Reflowable

Designed primarily for:

* novels
* essays
* memoirs
* business books
* technical books
* general nonfiction

The reader can change:

* font size
* reading width
* font
* device
* orientation

EPUB's default model is reflowable, where content adapts to the reader's viewport. ([W3C][4])

## Fixed / pre-paginated

Designed for:

* children's books
* illustrated books
* comics
* graphic novels
* cookbooks
* highly visual publications
* complex page compositions

The visual arrangement of the page is preserved.

EPUB supports both reflowable and fixed-layout publication models. ([W3C][4])

### Architecture implication

The suite should therefore have:

```text
Book Layout
│
├── Reflowable Engine
│ ├── Text flow
│ ├── Dynamic pagination
│ ├── Responsive images
│ └── Reader-controlled typography
│
└── Fixed Layout Engine
├── Page canvas
├── Absolute positioning
├── Image placement
├── Text boxes
└── Page-level composition
```

### Haptics

Haptics should communicate state rather than decorate the interface:

* selection → light feedback
* snapping → subtle tick
* successful action → confirmation pulse
* boundary → resistance/pulse
* invalid action → warning pulse
* export completion → completion pattern

Unsupported devices simply fall back to visual/audio feedback.

# 27. AI Interaction Architecture

AI should not dominate the interface.

Instead:

```text

↓
Contextual AI action
↓
AI command panel
↓

↓
```

One important architectural conclusion from the research is that the suite should be built around a **semantic Book Model**, rather than treating the eBook as a giant editable document. That model is what allows the same content to become reflowable EPUB, fixed-layout EPUB, PDF, web output, previews, accessible publications, and AI-manipulable content. EPUB itself is fundamentally a packaged, structured representation of HTML/CSS/SVG and related publication resources. ([W3C][5])
