# GS-PIXELS V2 — ENGINEERED IMPLEMENTATION SPEC

ROLE
You are the principal software architect, senior frontend engineer, UX systems designer, and PWA performance engineer for GS Softwares.

MISSION
Upgrade the existing GS-Pixels PWA into a production-grade, privacy-first, browser-native image workstation while preserving all working functionality.

The goal is NOT to redesign a screenshot.
The goal is to evolve the existing codebase into a scalable platform architecture.

==================================================
0. NON-NEGOTIABLE RULES
==================================================

1. INSPECT BEFORE MODIFYING.
   Never assume the current framework, file structure, state model, storage model, or processing pipeline.

2. PRESERVE FUNCTIONALITY.
   Existing working features, routes, processing logic, import/export behavior, and PWA functionality must continue working unless deliberately replaced with an equivalent or superior implementation.

3. NO BIG-BANG REWRITE.
   Prefer incremental refactoring and adapter layers.

4. NO FAKE FEATURES.
   Do not create buttons, APIs, services, or UI that appear functional but are not implemented.

5. NO UNNECESSARY DEPENDENCIES.
   Reuse existing libraries when appropriate.

6. SEPARATE UI FROM PROCESSING.
   Heavy image work must not unnecessarily block the main UI thread.

7. PRIVACY CLAIMS MUST BE TRUE.
   Never display "local", "private", or "offline" when data is actually sent externally.

8. GLOBAL STORAGE IS A PLATFORM SERVICE.
   GS-Pixels must not own an isolated storage architecture.

9. ACCESSIBILITY, PERFORMANCE, SECURITY, AND RECOVERY ARE CORE REQUIREMENTS.

10. DO NOT OPTIMIZE FOR VISUAL APPEARANCE AT THE COST OF ARCHITECTURAL QUALITY.

==================================================
4. GLOBAL STORAGE — FIRST-CLASS PLATFORM LAYER
==================================================

IMPORTANT:

Global Storage is NOT window.localStorage.

Create a storage abstraction independent of UI and independent of GS-Pixels.

Use the most appropriate browser technologies available in the current project:

- IndexedDB → metadata, structured records, indexes, project state
- OPFS → large binary assets where appropriate
- Cache Storage → PWA/cache assets
- localStorage → only small preferences/configuration

Do not store large binary files in localStorage.

Create a stable asset abstraction conceptually equivalent to:

Asset {
    id
    name
    type
    mimeType
    size
    checksum
    createdAt
    modifiedAt
    sourceApp
    folderId
    tags
    versions
    linkedAssets
}

Create a storage service/interface similar to:

createAsset()
getAsset()
updateAsset()
deleteAsset()
listAssets()
searchAssets()
moveAsset()
duplicateAsset()
createVersion()
getVersions()
restoreVersion()
getStorageUsage()

The exact API must match the existing technology stack.

IMPORTANT:
UI components must not directly manipulate IndexedDB/OPFS.

Use:

UI
 ↓
Workspace/Domain State
 ↓
Storage Service
 ↓
Storage Adapter
 ↓
IndexedDB / OPFS / Cache

==================================================
5. GLOBAL ASSET MODEL
==================================================

Assets must have stable IDs.

Applications should reference assets by ID rather than repeatedly duplicating large files.

Example:

GS-Pixels
   ↓
asset_123
   ↓
Global Storage

GS-Canvas
   ↓
asset_123
   ↓
Global Storage

Where safe and practical:

- content hashing
- deduplication
- reference counting
- version tracking

Do not introduce unsafe deduplication that can cause one user's mutation to unexpectedly alter another logical asset.

==================================================
6. GLOBAL STORAGE CATEGORIES
==================================================

Explicitly distinguish:

PERSISTENT ASSETS

- missing binary data
- stale references
- browser limitations

Do not claim unlimited storage.
